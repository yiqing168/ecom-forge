# 01 架构与交易契约

| 项       | 内容                                                                                  |
| -------- | ------------------------------------------------------------------------------------- |
| 状态     | v0.2 1A 生成动作证据与无费用卡交易路径回写后可复审                                    |
| 基准     | PRD v1.11                                                                             |
| 完成节点 | Bootstrap 前                                                                          |
| 裁决范围 | 模块边界、R1-R5 工程落地、交易总契约、积分预留、Provider 回执、商品保真接口与三级处置 |
| 不裁决   | 具体表结构、状态枚举、API payload、UI 文案、验收脚本                                  |

## 1. 目标

阶段 0 必须先把“谁能生成、谁能修改、谁被收费、失败怎么退款、Provider 回执怎么算数”固定下来。否则 1A 一旦接入真实模型和积分，最容易出现重复扣费、错误重试、产物归属混乱和申诉不可审计。

本文定义平台的最高工程契约：

- 三个创作入口共用同一执行引擎。
- 产物修改权按系统元数据确定，不由 LLM 判断。
- 所有可收费任务必须先有积分预留，再有工作流运行。
- Provider 请求离开平台后，重试和退款必须按回执状态处理。
- 每个运行快照必须固定 Skill、模型、提示词编译结果、计价版本、规范版本和商品事实版本。
- 商品保真、平台规范和内容安全是三条不同链路。

## 2. 系统模块边界

| 模块                 | 职责                                                                            | 不负责                                               |
| -------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Agent                | 在用户已选主 Skill 边界内理解输入、按白名单加载辅助知识、生成候选计划并解释结果 | 选择/替换主 Skill、直接绕过权限、扣费或调用 Provider |
| 确定性计划编译器     | 校验引用权限、R1-R5、费用、幂等键、模型能力和 Skill 版本，生成可执行 DAG        | 创意判断、自然语言闲聊                               |
| 统一模型网关         | 封装 Provider 能力、入参出参、回执、错误分类、熔断和成本记录                    | 决定业务状态、直接修改账本                           |
| Workflow 引擎        | 执行 `workflow_run -> task -> task_attempt -> artifact`，支持恢复、重试和日志   | 持有积分余额真相                                     |
| 积分账本             | 冻结、结算、解冻、申诉退款、人工冲正                                            | 调用模型、存储产物文件                               |
| 资产服务             | 上传、存库、签名 URL、删除生命周期、分享可见性                                  | 判断生成结果是否合规                                 |
| 商品事实与保真校验器 | 按用户确认事实和必需参考图识别商品事实风险                                      | 平台规范审核、法律/内容安全硬拦截                    |
| 平台规范引擎         | 平台规则存储、Prompt 注入、尺寸/白底/OCR 等输出校验                             | 商品 SKU 保真判断                                    |
| 内容安全链路         | 违法违规、平台禁用项、敏感内容审核                                              | 商品事实准确性判断                                   |

## 3. 三入口统一执行模型

Agent、画布、套图都是执行引擎的不同外壳：

产品形态红线：1A 的主入口是对话 Agent，承接创意生图、电商从零生成和本会话产物迭代；画布是后续工作流模块，不是 1A 对话 Agent 的产品形态。1A 的对话流程独立于画布，不要求用户先建立节点或编排工作流。

| 入口  | 计划来源                     | 典型任务                           | 修改出口                                     |
| ----- | ---------------------------- | ---------------------------------- | -------------------------------------------- |
| Agent | LLM 生成，经确定性编译器校验 | 商品白底精修、本会话改图、创意生成 | 本会话产物可继续对话改；电商产物也可送入画布 |
| 套图  | 固化表单工作流               | 主图套图、详情页、A+ 图            | 送入画布后修改                               |
| 画布  | 用户手动编排 DAG             | 节点生成、节点指令编辑、整链运行   | 画布内修改                                   |

真实执行状态只能落在：

```text
workflow_run -> task -> task_attempt -> artifact
```

`dag_json` 只保存计划快照，不作为运行时真相。积分预留、Provider 回执、任务重试、模型版本、Skill 版本、提示词编译结果、计价版本、规范版本、商品事实版本和产物谱系都必须能从上述模型追溯。

## 4. R1-R5 工程落地

| 规则                                      | 服务端实现                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------------ |
| R1 对话是敏捷生成入口                     | `trigger_mode=chat` 的 `workflow_run` 可创建创意和电商产物；会话内产物可继续对话迭代 |
| R2 画布是专业编排和非对话电商产物修改出口 | 画布/套图产物进入改图时必须挂载为画布素材节点                                        |
| R3 套图是电商标准出图快速通道             | 套图产物保留套图任务 ID、参数快照和商品事实版本，可送入画布                          |
| R4 创意到电商是单向资产桥                 | 创意产物可存资产库后被画布/套图引用；引用不改变原产物修改权                          |
| R5 谁生成谁负责改                         | 修改权只按 `producer_mode`、`producer_session_id`、`mutation_owner` 判断             |

每个系统一等产物必须持久化：

```json
{
  "producer_mode": "chat | canvas | suite",
  "producer_session_id": "chat session id when producer_mode=chat",
  "mutation_owner": "chat_session | canvas | suite",
  "origin_domain": "creative | commerce"
}
```

阶段 1B 的 `trigger_mode=batch` 只是一次报价/运行下的批量编排来源，不新增 `producer_mode=batch` 或修改权 owner。每个 batch item 必须按其实际配方落为 `chat` 或 `suite` 产物；批量聚合不能成为绕过 R1-R5 的第四种产物入口。

执行前必须做确定性校验：

| 请求                       | 允许             | 拒绝/引导                                        |
| -------------------------- | ---------------- | ------------------------------------------------ |
| 当前会话继续修改本会话产物 | 允许             | 无                                               |
| 当前会话修改其他会话产物   | 拒绝             | 引导新会话或资产引用                             |
| 对话修改画布产物           | 拒绝             | 跳转画布并自动挂载                               |
| 对话修改套图产物           | 拒绝             | 跳转画布并自动挂载                               |
| 画布引用对话产物           | 允许作为素材引用 | 不改变原对话产物修改权；画布生成的下游产物归画布 |
| 新上传原始素材用于生成     | 允许             | 不继承任何旧产物修改权                           |
| 下载后再上传的文件         | 允许作为新素材   | 不得伪装为系统既有产物                           |

LLM 只负责解析用户指代和意图，不能用提示词判断产物来源或放行请求。

系统只按携带 `artifactId` 的一等产物元数据判断修改权。用户重新上传、下载后再上传或从站外导入的文件均视为新的原始素材；平台不得依赖 EXIF、隐写水印或图像相似度猜测其生产入口并据此拦截。

## 5. 交易总契约

所有可收费任务遵循同一交易流程：

```text
费用预估
  -> 用户确认或提交即确认
  -> 创建 credit_reservation
  -> 创建 workflow_run
  -> 创建 task
  -> 创建 task_attempt 并投递 Provider
  -> 成功产出 artifact
  -> 从 reservation 结算
```

失败流程：

```text
Provider 未送达
  -> 可自动重试，最多 2 次
  -> 最终失败后解冻未结算 reservation
  -> 写入 credit_ledger release 类型

Provider 已明确终局失败
  -> 标记任务失败
  -> 解冻未结算 reservation
  -> 写入 credit_ledger release 类型

Provider 已受理但结果未知
  -> 标记 outcome_unknown
  -> 保留原 reservation 冻结
  -> 用户可明确发起新的收费生成动作，原请求绝不自动重投
  -> 自 unknown attempt 的服务端 ended_at 起满 30 分钟，自动释放原请求未结算冻结并标记失败；不以之后收到的回执为条件
  -> 进入 outcome_unknown 后收到的成功/失败回执（含 30 分钟内）只记内部异常，不自动发布产物、消费原冻结或补扣用户积分
```

申诉流程：

```text
用户从积分流水发起申诉
  -> 运营审核
  -> 通过时写入 appeal_refund 流水
  -> credit_accounts 由 ledger 投影更新
```

## 6. 提交证据与积分核对规则

| 场景                  | 提交语义                                                                |
| --------------------- | ----------------------------------------------------------------------- |
| 1A 创意生成           | 点击生成形成 `generate_action@v2`；Brain 解析张数后报价、核对并直接预留 |
| 1A 电商生成           | 必要商品事实确认后走同一直接预留路径，不增加费用卡                      |
| 价格/余额/数量异常    | Provider 前就地阻断并保留输入，不降数量、不换模、不转二次确认           |
| 1A 计划或目录发生漂移 | 当前动作失效；刷新权威目录后由用户重新点击生成                          |
| 批量/套图/画布        | 点击开始生成或运行即授权当前动作；后台报价、核对并预留，不弹确认框      |
| 人工/用户明确重试     | 创建新的幂等提交证据、quote、reservation，并提示必要的重复生成风险      |

## 7. 积分预留契约

不变量：

- 每次任务提交必须在同一数据库事务中创建不可变 `credit_reservation`、冻结流水和 `workflow_run`；不得产生无预留的收费运行态。
- 多步任务按总预估一次冻结，子任务只从该预留结算。
- 冻结、结算、解冻、申诉退款和人工冲正必须通过同一服务端事务及幂等键写入账本。
- `credit_ledger` 是不可篡改审计来源，`credit_accounts` 只是余额投影。
- 刷新、重连、重复点击和 Worker 恢复不得创建第二次付费调用。
- task 级使用稳定幂等键；每次实际 Provider 投递必须形成独立 `task_attempt` 和递增 `attempt_no`。

预留状态由 `04` 裁决，字段由 `05` 裁决，接口由 `06` 裁决。

## 8. Provider 回执契约

Provider 投递状态至少区分：

| dispatch_state    | 含义                             | 自动重试        | 交易处理                                            |
| ----------------- | -------------------------------- | --------------- | --------------------------------------------------- |
| `not_dispatched`  | 本地确认未送达 Provider          | 允许，最多 2 次 | 不重复计费                                          |
| `accepted`        | Provider 已有请求 ID 或受理回执  | 不允许自动重投  | 等待 Provider 终局；用户可另发新收费动作            |
| `outcome_unknown` | 请求可能已离开平台，最终结果未知 | 不允许自动重投  | 用户可立即另发新收费动作；30 分钟超时自动释放原冻结 |

Provider 回执原文必须保存摘要，至少包括：

- provider 名称和模型版本。
- provider_request_id。
- 提交时间、受理时间、完成时间。
- 回调/轮询来源。
- 原始错误码和错误摘要。
- 成本相关字段。

## 9. 商品保真接口

商品保真校验器独立于平台规范和内容安全。

输入：

```json
{
  "artifact_id": "generated artifact",
  "product_fact_set_id": "confirmed facts",
  "required_reference_asset_ids": ["asset id"],
  "task_snapshot": "model, prompt, params, skill version",
  "evaluator_version": "commerce-evidence@version"
}
```

输出：

```json
{
  "status": "pass | warning | unknown | blocked",
  "findings": [],
  "confidence": 0.0,
  "evidence_snapshot": {},
  "recommended_action": "none | show_warning | require_confirmation | hard_block"
}
```

## 10. 保真三级处置

| 处置                     | 含义                                                 | 阶段      |
| ------------------------ | ---------------------------------------------------- | --------- |
| `unknown`                | 证据不足或校验器无可靠结论，只提示未知               | 1A 起     |
| `high_risk_confirmation` | 高风险但无法可靠判定，用户确认后可导出，记录证据快照 | 2B 校准后 |
| `hard_block`             | 与已确认商品事实存在确定冲突，阻止作为上架素材导出   | 2B 校准后 |

规则：

- 1A 只输出 `warning/unknown`，商品事实冲突不自动硬拦。
- 2B 校准后，启用高风险确认；仅对确定事实冲突启用 `hard_block`。
- 法律/平台禁用项由内容安全链路独立硬拦截。
- 保真校验器不得自动重试，不得替用户改写商品事实。
