## 1. 总体判断

全项目不应拆成几十上百个小 SPEC。按 PRD 当前范围，建议控制为 **25 个完整开发 SPEC**：

- 每个 SPEC 是一个完整交付包，不是一个小函数或一个小接口。
- 每个 SPEC 必须覆盖它涉及的 UI、API、DB、Worker、测试、验收和运营日志。
- 本计划中的 `D` 定义为 development week（开发周），`1D = 5 个工作日`，不是自然日、迭代编号或人日。
- 原团队测算基准为 2 名全栈工程师 + 1 名前端工程师；当前实际执行资源为 1 名开发者，因此所有 SPEC 按依赖串行，不承诺多角色并行。
- 1A 预计总工作量 30-75 人日；单开发者理论工期约 6-15 个工作周，Provider PoC、UI 评审和外部服务申请另计风险缓冲。实际交付日期必须在首轮 PoC 和 S01/S02 完成后滚动校准。
- 一个 SPEC 预计 2-5 个开发日；当前由单开发者串行完成，不因资源约束拆成零散功能票。
- 其中 1A 封闭内测上线为 **15 个 SPEC**，后续阶段为 **10 个 SPEC**。

每个 SPEC 的完成流程固定为：

```text
实现与自动化测试
  -> Codex 审查完整代码 diff
  -> 修复发现并重新验证
  -> Codex 明确报告“代码审查通过”
  -> 用户验收
  -> 用户明确验收通过
  -> 才允许 git commit
```

代码审查通过与用户验收通过是两个独立门禁。任何测试成功、审查结论或任务状态更新都不得替代用户验收；用户未明确验收通过时禁止提交、合并或推送。

所以当前阶段的目标不是“立刻能上线”，而是：

```text
先评审并冻结 15 个 1A 上线 SPEC
  -> 再按 SPEC 编码
  -> 全部通过测试和上线门禁
  -> 才能封闭内测上线
  -> 再按 1B/2A/2B/3a/3b/4 继续追加上线
```

## 2. 产品形态总边界

1A 第一入口是对话 Agent，用于：

- 创意生图。
- 电商从零生成。
- 本会话产物继续改图。
- 商品白底精修闭环。

“电商从零生成”只表示用户无需预先建立商品档案，可在对话中快速创建商品并确认事实；首版白底精修仍必须有用户授权的商品原图，不支持仅凭文本臆造真实商品。

画布是后续专业工作流模块，不进入 1A 主交互：

- 1A 不做完整画布工作台。
- 1A 不要求用户先进画布才能创意生图或电商生成。
- 1A 只保留未来“送入画布”所需的数据，不显示入口或不可用占位，也不实现画布编辑体验。
- 阶段 3a/3b 再实现画布节点、节点版本、DAG 编排、节点指令编辑和整链运行。

## 7. 推荐开发顺序

阶段 0 的 S07 PoC 是关键路径，但当前只有 1 名开发者：先完成 S01、S02，再立即执行 S07 PoC spike；等待 Provider 资质、额度或异步结果期间可穿插 S03-S06。真实 Provider 不可行或成本未冻结时，不进入任何可收费链路编码。

第一批，先把工程、队列和资金底座跑通：

```text
S01 -> S02 -> S03 -> S05 -> S04 -> S06
```

S05 先提供 workflow/queue/worker/settlement job 的执行底座，S04 随后实现资金事务并与 S05 联调；两者完成后才允许 S06 接入终态事件。

第二批，接 Agent 和权限：

```text
S07 PoC spike（S01/S02 后优先） -> S07 Gateway（D2-D5） -> S08 -> S09 -> S10
```

第三批，先完成最小控制面，再做 1A 前台与图片闭环：

```text
S14A -> S11 -> S12 -> S13A -> S13B
```

S14A 必须先交付独立管理员身份、邀请码、local/test Provider/Storage 控制面、Brain/图片模型目录、图片规格积分定价和最小审计，S11 才能消费已发布的用户可选模型目录；S11 同时交付 11 个 1A primary、7 个热门类目和通用 auxiliary 的正式内容包。S12 复用目录并激活图片执行、安全审核、发布公共管线与白底精修；S13A/S13B 再分两步激活全部 10 个创意 primary。腾讯 COS 生产 adapter 与真实桶 smoke 归 S15 上线门禁，未通过前 staging/beta/production 存储 fail closed。视频模型在 S14A 只能保存 draft；S16 的 PoC 与上线门禁通过前不得批准、定价或发布。

第四批，补齐运营台并执行上线门禁：

```text
S14B -> S15
```

第五批，1A 之后再做：

```text
1B: S16 -> S17 -> S18
2A: S19 -> S20 -> S21
2B + 3a: S22 -> S23 -> S24（S22 只预留画布挂载数据，S24 完成后才显示并开放“送入画布”入口）
3b: S25
```

1B 开工前先启动由 S16 负责的视频 Provider PoC spike；PoC 与准备工作可并行，但必须在 S16 的视频网关和收费功能编码前通过成本评审。S17 的高清放大模型同样先 PoC、后进入收费路由。

S22 可先完成开发和 staging 验收，但包含套图能力的 2B 对外发布必须等待 S24，通过同一发布门禁后一起开放；不得先公开一个没有修改出口的套图产品。

S23 的保真校准数据工作流从 2A 开始，由产品、算法/工程和运营共同准备并双人复核，不占用 S23 的 2-5 日工程实现窗口；S23 开工前必须提供已版本化的校准集和 holdout。校准门禁未通过时，S23 不得签字完成，2B 对外发布保持阻塞。

## 8. UI 设计任务排布

UI 不作为“最后美化”，而是进入对应业务任务。成熟产品证据、采用/拒绝理由、正反流程和全站详细清单统一见 `docs/research/01-full-site-product-interaction-benchmark.md`；本节只裁决设计批次、数量和开发归属。

所有产品 UI 编码前必须先通过设计门禁：

1. 先审阅本地 `imgage/` 和调研文档，只提取成熟信息架构、布局密度和交互模式；参考目录由 Git 忽略，不复制品牌、视觉外观和不适合本项目的产品形态。
2. 页面计数按“页面族”而不是每个状态截图：同一 master-detail/workbench 壳承载的列表/详情、Tab 和状态复用一族，主任务与交互骨架不同才单列；overlay 单独计数。
3. 使用 Stitch MCP 建立一套设计系统，再分组产出。第一组通过产品评审并冻结后，才开始 S11-S14A 正式产品 UI 编码；S14B 与后续组可以先完成设计，不等于提前开放功能。
4. Stitch MCP 不可用、页面清单未评审或设计稿未冻结时，只允许推进非产品 UI 的工程/API/数据任务，不得自行臆造正式界面。
5. 1A 第一入口始终是对话 Agent；画布只在第三组出现。Agent 可以规划执行，但用户只确认必要事实/风险，不确认费用，也不存在“计划确认”。

### 8.3 Stitch 交付规则

1. 每组先生成桌面主态；移动端对 A01-A10、B01-B09 给出可操作布局；O02/O05-O08 随 S14A 评审，O01/O03-O04/O09-O12 随 S14B 评审，O13 随 S12/S14B 激活；管理台移动端只支持查询和明确允许的紧急熔断，高风险批量发布仅桌面；C02 只给只读/任务/预览/下载态。
2. 第一组必须串成可点击主流程：注册邀请 -> 新会话 -> 上传商品图 -> 事实确认 -> Brain 解析张数 -> Compiler/Credit 积分核对与预留 -> 任务 -> 结果 -> 继续改 -> 存资产/下载 -> 流水；创意与电商都不插费用卡。
3. 第二组必须串成 DesignKit 式套图流程和批量部分失败流程；不把套图表单塞进 Agent。
4. 第三组必须展示商品原图 -> 精修 -> 裂变 -> 图生视频的手工 DAG，包含上游附件自动进入、手动附件节点化、附件域内 `@`、单节点/整链单动作运行、Provider 前积分核对、失败和版本回退。
5. 设计稿必须标注路由、页面族 ID、状态、API/SSE 依赖、桌面/移动范围；不能只给静态 happy path。
6. 任何新增核心页面、全局入口或确认步骤必须先修改调研文档、PRD/对应契约和本节，再重新评审。

每个包含 UI 的 SPEC 必须写：

- 对应的已评审 Stitch 设计稿、页面族 ID 和页面清单。
- 页面路径或组件路径。
- 状态列表：loading、empty、success、error、permission denied、retrying、SSE reconnecting。
- 移动端和桌面端布局要求。
- 与后端 API/SSE 的字段映射。
- 至少一个 Playwright E2E 或组件测试。

## 10. 上线门禁

达到以下条件前，不得称为“能上线”：

- P0 SPEC 全部完成并通过代码评审。
- `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm test:integration`、`pnpm test:worker`、`pnpm test:e2e` 通过。
- `pnpm db:check` 和迁移回滚演练通过。
- 上述验收脚本归属表中的全部命令通过，包含 `pnpm validate:ledger-replay`。
- Provider PoC 至少覆盖 1 个图片生成模型和 1 个图片编辑模型。
- Agent Brain PoC 至少覆盖 1 个真实推理模型的 strict tool/terminal、usage、超时和成本预算路径；fake Brain 不能作为上线证据。
- 成本核算工作表完成，积分锚定价和内测赠送额度已拍板。
- SSE 心跳、断线恢复和 watchdog 验证通过。
- outcome_unknown 30 分钟自动释放、迟到回执死信且不补扣验证通过。
- S14A 可完成邀请码和真实模型/价格 catalog 配置，S11/S12 不依赖写死配置；S14B 的完整运营、风控和审计模块通过验收。
- S11 的 11 个 1A primary、7 个热门类目和通用 auxiliary 均为正式可复现内容包，S12/S13A/S13B 已用真实图片链路激活并通过 golden eval、资金、安全、恢复和浏览器验收。
- 香港/中国部署 smoke、监控告警、备份和回滚流程通过。
- 安全合规检查通过：签名 URL、隐私协议、密钥管理、审计日志；产品水印和 AI 标识不属于 1A 验收项。

1B 及后续阶段发布还必须满足：该阶段 SPEC 全部完成、该阶段专项 `validate:*` 全部通过、新 Provider/模型完成独立 PoC 和成本审批。S23 的 hard block、S24 的画布入口等带开关能力，在专项门禁通过前必须保持关闭。

## 11. 单个 SPEC 粒度规则

正式 SPEC 不按函数、小接口、小表拆。每个 SPEC 必须满足：

- 能交付一个用户或工程可感知的完整闭环。
- 能在 2-5 个开发日内完成；超过 5 天才允许拆成两个 SPEC。
- 必须写明开工前必读文档。
- 必须写明前端、后端、数据库、Worker、Provider、测试、监控是否涉及。
- 涉及资金和权限的 SPEC 必须包含集成测试和异常测试。
- 涉及 UI 的 SPEC 不允许只写页面，还必须写 API/SSE 字段映射和 Playwright/组件测试。
- 画布相关 SPEC 只允许出现在 S24/S25，不得混入 1A Agent 工作台。
